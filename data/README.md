# Data

All data is **synthetic**, generated by [`src/data_generation.py`](../src/data_generation.py)
for a fictional distributor. No employer, customer or proprietary data is used.

```bash
python -m src.data_generation              # clean extract, seed 42 -> data/raw/
python -m src.data_generation --seed 7     # a different, equally realistic world
python -m src.data_generation --dirty      # also write a copy with ERP defects -> data/raw_dirty/
```

The same seed always produces identical files. All folders here are
git-ignored because everything is reproducible.

| Folder | Contents | Used by analytics? |
|---|---|---|
| `raw/` | The six operational tables an ERP would export: **the source of record, never modified** | **Yes (default)** |
| `raw_dirty/` | Same extract with 25 documented ERP defects (optional) | No, only to demonstrate validation |
| `processed/` | Parquet exports of the analytics views (`python -m src.database export`) | Yes (Phase 4+) |
| `synthetic_truth/` | Generator answer key: intended pattern per SKU, archetype per supplier, injected-defect manifest | **No, validation only** |

Column definitions: [`docs/data_dictionary.md`](../docs/data_dictionary.md).
How the data was generated and why: [`docs/assumptions.md`](../docs/assumptions.md#synthetic-data-phase-2).

## Why the answer keys are separate

The generator knows which SKUs it *meant* to be seasonal, which suppliers it
*meant* to be unreliable, and which rows it corrupted in dirty mode. That is
useful for checking the generator and the validation checks, but it must never
become an analytical input: a real company has no such labels. Keeping it in
its own folder, with no shared column names, makes accidental use obvious, and
a test checks that no raw table contains pattern, archetype, ABC or XYZ columns.
