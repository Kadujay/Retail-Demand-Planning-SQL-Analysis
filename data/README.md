# Data

All data is **synthetic**, generated by [`src/data_generation.py`](../src/data_generation.py)
for a fictional distributor. No employer, customer or proprietary data is used.

```bash
python -m src.pipeline              # generate (seed 42) + validate
python -m src.pipeline --seed 7     # a different, equally realistic world
SYNTHETIC_DATA_SEED=7 python -m src.pipeline
```

The same seed always produces identical tables. The folders are git-ignored
because everything is reproducible. The data-quality report is written to
[`outputs/data_quality_report.csv`](../outputs/data_quality_report.csv) and is committed.

| Folder | Contents | Used by analytics? |
|---|---|---|
| `raw/` | The six operational tables an ERP would export | **Yes** |
| `processed/` | Validated / enriched tables (from Phase 3) | Yes |
| `synthetic_truth/` | The generator's answer key: intended demand pattern per SKU, archetype per supplier | **No — validation only** |

### Why the answer key is separate

The generator knows which SKUs it *meant* to be seasonal and which suppliers it
*meant* to be unreliable. That metadata is useful for checking the generator
(see `notebooks/01_data_exploration.ipynb`), but it must never become an
analytical input: a real company has no such labels, and a model that used
them would be cheating. Keeping it in its own folder, with no shared column
names, makes accidental use obvious. A test checks that no raw table contains
pattern, archetype, ABC or XYZ columns.

## Row counts (seed 42)

| Table | Grain | Rows |
|---|---|---|
| `suppliers` | Supplier | 50 |
| `products` | SKU | 5,000 |
| `demand_monthly` | SKU × month, from launch month | 114,424 |
| `inventory_snapshot` | SKU × month-end, from launch month | 114,424 |
| `purchase_orders` | PO line | 35,684 |
| `supplier_deliveries` | Receipt event | 36,907 |

SKU-month tables have fewer than 5,000 × 24 rows because SKUs launched during
the window have no rows before launch.

## Raw data dictionary

### `suppliers.csv`
| Column | Type | Description |
|---|---|---|
| supplier_id | text, PK | `SUP-001` … |
| supplier_name | text | Neutral placeholder name |
| region | text | `Domestic` / `Import` |
| quoted_lead_time_days | int | Supplier's standard quoted lead time |

### `products.csv`
| Column | Type | Description |
|---|---|---|
| sku_id | text, PK | `SKU-00001` … |
| category | text | One of 8 product categories |
| supplier_id | text, FK | Primary supplier |
| unit_cost | decimal | Standard cost (USD) |
| unit_price | decimal | Selling price (USD) |
| moq | int | Supplier minimum order quantity (units) |
| order_multiple | int | Case pack; orders are rounded up to this |
| supplier_lead_time_days | int | Quoted lead time for this SKU |
| launch_date | date | First date the product was sellable |
| lifecycle_status | text | ERP status: `ACTIVE` / `NEW` / `DISCONTINUED` (maintained imperfectly, as in real item masters) |

### `demand_monthly.csv` — customer demand vs. shipments
| Column | Type | Description |
|---|---|---|
| sku_id, month_start | PK | |
| ordered_qty | int | **Customer demand**: units customers ordered |
| shipped_qty | int | **Customer shipments**: units delivered (≤ ordered; the gap is lost sales from stockouts) |

### `inventory_snapshot.csv` — on-hand inventory
| Column | Type | Description |
|---|---|---|
| sku_id, month_end | PK | |
| on_hand_qty | int | Physical stock at month end |
| allocated_qty | int | Committed to customer orders, not yet shipped (≤ on hand) |

Stock flow reconciles exactly: `on_hand(t) = on_hand(t−1) + receipts(t) − shipped(t)`.

### `purchase_orders.csv` — orders placed with suppliers
| Column | Type | Description |
|---|---|---|
| po_line_id | text, PK | `PO-000123-02` (PO number + line) |
| po_number | text | One PO per supplier per order date |
| sku_id, supplier_id | FK | |
| order_date | date | When the PO was placed |
| promised_date | date | Original promised delivery date (order date + quoted lead time) |
| ordered_qty | int | Units ordered (≥ MOQ, multiple of order multiple) |
| unit_price | decimal | Purchase price (differs from standard cost → PPV) |
| status | text | As of 2025-12-31: `OPEN` (nothing received), `PARTIALLY_RECEIVED`, `CLOSED` (fully received), `CLOSED_SHORT` (remainder written off) |

**Open purchase orders** = lines with status OPEN or PARTIALLY_RECEIVED; open
quantity = ordered − received to date.

### `supplier_deliveries.csv` — received purchase orders
| Column | Type | Description |
|---|---|---|
| receipt_id | text, PK | `RCV-0000001` … |
| po_line_id | text, FK | PO line received against |
| receipt_date | date | Goods-receipt date (always after order date, never after as-of) |
| received_qty | int | Units received; several receipts per line = partial delivery |

## Synthetic truth (validation only)

`synthetic_truth/sku_generation_truth.csv`: intended pattern, base demand,
seasonal amplitude and peak, trend, noise CV, occurrence probability,
end-of-life month and the simulated buyer's cover.
`synthetic_truth/supplier_generation_truth.csv`: archetype and behavioural
parameters. How these were drawn is documented in
[`docs/assumptions.md`](../docs/assumptions.md#synthetic-data-phase-2).
